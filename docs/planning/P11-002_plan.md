## Objective

Define the implementation-ready architecture for async connector-aware bulk export without reopening P11-001 or reintroducing app-retained originals.

P11-002 is intentionally separate from P11-001.

- P11-001 covers capability-aware batch reanalysis only
- P11-002 covers bulk export only

The plan preserves the existing ARCH-002 boundary:

- originals for reference-mode items remain source-owned
- no hidden fallback to app-retained originals is allowed
- local-folder reference items do not gain fake hosted-original behavior
- bulk export must not assume provider-neutral bulk fetch by default

---

## Current Legacy Baseline

The live route in `src/api/routes/download.py` currently behaves as a legacy full-storage synchronous ZIP endpoint:

- it uses `POST /api/v1/media/download-batch`
- it builds the ZIP in the request thread
- it holds the ZIP in memory rather than using a temporary artifact lifecycle
- it silently skips items that are missing metadata or whose originals are not in app storage
- it returns only the ZIP response plus header counts, not explicit per-item eligibility reporting

That behavior is acceptable as a historical compatibility baseline, but it is **not** the final P11-002 contract.

### Locked product conclusion

Silent skip behavior and request-thread ZIP assembly are not acceptable as the final mixed full-plus-reference export contract.

## Architect Decision Summary

## Q1 — What exact API surface is in scope?

### Locked decision

P11-002 introduces a dedicated async export-job surface rather than extending the existing synchronous route into the final mixed-selection contract.

The implementation-ready in-scope surface is:

1. `POST /api/v1/media/export-batch`
2. `GET /api/v1/media/export-jobs/{job_id}`
3. `GET /api/v1/media/export-jobs/{job_id}/download`

### Legacy compatibility rule

`POST /api/v1/media/download-batch` remains a legacy full-storage compatibility route for now, but it is not the target P11-002 contract and must not be upgraded into the mixed full-plus-reference export model.

### Explicitly out of scope

- `POST /api/v1/media/reanalyze-batch`
- `GET /api/v1/media/{id}/download`
- provider-neutral bulk fetch for every reference provider
- browser-direct cloud export without a server-managed job
- permanent export archive storage

### Consequence

P11-002 creates a new export-job boundary instead of stretching the synchronous ZIP route beyond its safe design limits.

## Q2 — What is the user-facing export contract for mixed selections?

### Locked decision

Mixed selections are allowed, but the submission step must classify every requested item explicitly.

The submission response must classify each requested item into one of these outcomes:

- `accepted` — eligible for export job processing
- `blocked` — owned by the caller but not eligible for server-side bulk export under the locked contract
- `rejected` — invalid for the request or not accessible to the caller

### Locked eligibility classes

1. **Full/app-retained items**
   - accepted
2. **Drive-backed `storage_mode='reference'` items**
   - accepted only through async export-job processing with connector-aware bounded fetch behavior
3. **Local-folder reference items**
   - blocked
4. **Future non-Drive reference providers**
   - blocked unless a later dedicated workstream explicitly expands them

### Minimum blocked reason classes

- `local_reference_not_supported`
- `provider_bulk_export_not_supported`
- `analysis_not_completed`
- `export_in_progress`
- `connector_refetch_not_available`

### Minimum rejected reason classes

- `media_item_not_found`

### Locked privacy rule

As with P11-001, missing and unauthorized IDs must collapse into privacy-preserving rejected `media_item_not_found`.

### Consequence

Mixed selection becomes an explicit eligibility-reporting contract, not a silent-skip contract.

## Q3 — Must exports become asynchronous job-based rather than synchronous ZIP-in-request?

### Locked decision

Yes. The final P11-002 contract must be asynchronous and job-based.

### Why this is the correct boundary

- Drive-backed export can require many upstream fetches and cannot safely run in the request thread
- ZIP assembly across mixed full and Drive-backed selections has a materially different operational profile than single-item download or batch reanalysis
- request-thread ZIP creation encourages memory spikes, long request duration, and weak failure reporting

### Consequence

The request only creates an export job. ZIP assembly happens asynchronously. Download happens only after the export artifact is ready.

## Q4 — What artifact lifecycle is required?

### Locked decision

P11-002 uses a temporary user-scoped export artifact lifecycle.

### Required lifecycle rules

- the ZIP artifact is created only for a specific export job
- the ZIP artifact is stored in a dedicated temporary export-artifact namespace, not as a `MediaItem`
- the artifact retention window is **24 hours maximum**
- the artifact must be deleted on the first successful download or on TTL expiry, whichever comes first
- expired or consumed artifacts must become non-downloadable and report a controlled expired-state error
- cleanup must run both on normal completion paths and via a best-effort sweeper on startup or periodic maintenance

### Retry behavior

- job submission does not create hidden automatic whole-job retries
- connector/transient failures remain item-scoped inside the job result
- if the user wants another export attempt, the user submits a new export job

### Consequence

P11-002 delivers temporary export artifacts, not a permanent export library.

## Q5 — What connector, rate-limit, and concurrency constraints are required?

### Locked decision

Drive-backed export requires explicit bounded execution and must not fan out unbounded connector fetches.

### Required safeguards

- keep the request size bounded
- Drive-backed fetches inside an export job must run under explicit bounded concurrency
- same-connector or same-source fetch bursts must be throttled conservatively
- ZIP creation must write incrementally to a temporary artifact rather than assembling the entire archive in memory

### Initial architectural expectation

- use a conservative Drive-fetch concurrency limit
- prefer sequential ZIP writing with bounded upstream fetch parallelism
- treat connector throttling as part of the locked contract, not an implementation detail

### Consequence

P11-002 preserves predictable resource use and avoids turning bulk export into a connector-thrashing background storm.

## Q6 — What explicit accepted/blocked/rejected reporting is required?

### Locked decision

Submission response and job result reporting are separate and both are required.

### Submission response contract

If at least one item is accepted, `POST /api/v1/media/export-batch` returns **HTTP 202** and includes:

- `job_id`
- `request_count`
- `accepted_count`
- `blocked_count`
- `rejected_count`
- `outcomes[]` for every requested item in request order

### No-eligible-items rule

If zero items are accepted, the route must create no job and return **HTTP 409** with standardized `detail` payload containing:

- `error_code: export_no_eligible_items`
- `message`
- `request_count`
- `accepted_count: 0`
- `blocked_count`
- `rejected_count`
- `outcomes[]`

### Job result contract

Accepted items are then tracked in the export job result as:

- `exported`
- `failed`

The job status model must include, at minimum:

- `pending`
- `running`
- `completed`
- `completed_with_failures`
- `failed`
- `expired`

### Consequence

Users get explicit answers at submission time and explicit runtime results after job execution.

## Q7 — What quota or billing implications apply?

### Locked decision

P11-002 does **not** consume the analysis quota model and does **not** introduce a new billing model in this slice.

### Required operational controls instead

- max items per request
- max active export jobs per user
- temporary artifact TTL
- bounded connector concurrency

### Consequence

P11-002 remains operationally bounded without entangling export planning with a broader billing redesign.

## Q8 — What security and privacy constraints apply to temporary export artifacts?

### Locked decision

Temporary export artifacts are sensitive derived files and must be treated as short-lived, user-scoped private artifacts.

### Required constraints

- artifact IDs and job IDs must be opaque and non-guessable
- every status and download route must be ownership-scoped
- artifacts must not be exposed through public URLs or persistent indexes
- artifacts must not be represented as gallery items or source objects
- metadata about blocked and rejected items must remain operator-safe and privacy-preserving

### Consequence

P11-002 adds temporary private export artifacts, not a reusable cross-session download vault.

## Q9 — What operator-safe error contract should govern export failures?

### Locked decision

P11-002 uses standardized `detail` plus `error_code` payloads for submission failures and explicit item-scoped job result failures for runtime export work.

### Minimum submission failure classes

- `export_batch_too_large`
- `export_job_limit_reached`
- `export_no_eligible_items`

### Minimum runtime item failure classes

- `drive_file_not_found`
- `drive_auth_expired`
- `drive_rate_limited`
- `drive_fetch_timeout`
- `drive_fetch_failed`
- `artifact_write_failed`

### Artifact download failure classes

- `export_job_not_found`
- `export_not_ready`
- `export_artifact_expired`

### Consequence

Submission errors, runtime item failures, and artifact-download failures remain distinct and debuggable.

## Q10 — What remains explicitly out of scope?

### Locked out-of-scope items

- local-folder server-side bulk export
- provider-neutral bulk fetch for all reference providers
- non-Drive provider enablement by default
- permanent export archive retention
- billing-model changes for export usage
- cross-job automatic retries
- deprecating or deleting the legacy synchronous `POST /api/v1/media/download-batch` route in this slice

## Service and API Changes

## 1. Add a dedicated async export-job boundary

P11-002 must not reuse the synchronous ZIP response as the final contract.

The system needs:

- an export-job creation route
- an export-job status route
- an export-artifact download route

## 2. Preserve legacy route compatibility without promoting it to the final contract

The existing `POST /api/v1/media/download-batch` route remains the historical compatibility baseline for full-storage-only ZIP export.

P11-002 does not require deleting or rewriting it immediately, but it must not be treated as the authoritative mixed-selection export contract.

## 3. Use submission-time eligibility classification plus runtime execution results

Submission-time blocked and rejected outcomes must be explicit.

Runtime execution results for accepted items must also be explicit after the job runs.

## 4. Use temporary export artifacts rather than persistent originals or permanent ZIPs

P11-002 may create a temporary ZIP artifact, but it must not create a new permanent original-retention path.

---

## Compatibility Rules

## Local-folder behavior

Local-folder reference items remain user-mediated source items.

P11-002 must not imply that the backend can bulk-read those originals from hosted storage.

## Drive-backed behavior

Drive-backed reference items are the only connector-backed reference class eligible for server-side bulk export in this slice.

## Future providers

Non-Drive reference providers remain blocked by default.

Any future provider expansion must be explicit and connector-specific.

## Architect Verdict

P11-002 is architecturally and contractually reconciled to ADR-036.

The implementation landed inside the correct ADR-036 architecture, was briefly reopened when closeout drift was found, and is now back in alignment after the narrow remediation slice completed. The remaining workflow step is the final Auditor closeout re-pass. If that re-pass accepts the package, P11-002 can be closed without reopening architecture or scope.

The critical discipline remains unchanged: no provider-neutral assumptions, no hidden original retention, no local-folder server-side reach-through, no merger back into P11-001, and no promotion of the legacy synchronous `POST /api/v1/media/download-batch` route into the target contract.

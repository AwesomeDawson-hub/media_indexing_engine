## Architect Decision

`P12-002` should be implemented as a **measurement-first search-quality baseline slice that freezes a remembered-photo query set, a stable scoring contract, and a repeatable evaluation harness before any richer metadata, reranking, or multimodal retrieval work is allowed to claim improvement**.

Reasoning:

- The current search stack is broad-semantic and functional, but it has no benchmark contract for highly specific remembered-photo retrieval.
- Without a frozen query set and scoring rules, later workstreams will drift into anecdotal quality claims.
- The lowest-risk and highest-leverage first move is therefore to define evaluation, not to change retrieval logic immediately.
- This keeps later search-quality workstreams measurable, comparable, and auditable.

## Objective

Create the evaluation foundation for remembered-photo retrieval so every later search-quality workstream can be measured against the same query set, scoring rules, and reporting format.

The target outcome is a stable benchmark that answers a simple product question:

**When a user remembers a very specific photo in natural language, is the intended photo appearing first or at least near the top?**

P12-002 does not attempt to improve search quality directly. It defines how improvement will be measured.

---

## Current Live Baseline

The current search architecture is good enough for broad semantic recall but not yet optimized for remembered-photo retrieval:

- metadata extraction is broad but shallow
- embedding text is a flat stitched summary rather than a composition-aware structured representation
- retrieval is primarily one-stage vector recall over flattened metadata text
- current filters help with broad narrowing, not precise remembered-photo disambiguation
- current search tests validate correctness, scoping, and basic ranking behavior, not top-1/top-5 remembered-photo quality

The current implementation surfaces most relevant to this baseline are:

- `src/analysis/anthropic_provider.py`
- `src/analysis/schemas.py`
- `src/search/embedding_text.py`
- `src/search/indexing_service.py`
- `src/search/search_service.py`
- `src/api/routes/search.py`
- `tests/test_search.py`

This makes P12-002 the correct first workstream in the remembered-photo retrieval roadmap: it establishes evaluation before the system begins changing representation or ranking.

## Architect Decision Summary

## Q1 — What exactly is the benchmark supposed to measure?

### Locked decision

P12-002 measures **remembered-photo retrieval quality**, not generic semantic-search adequacy.

The benchmark must focus on natural-language remembered-photo queries such as:

- subject attribute recall
- spatial/compositional recall
- relationship recall
- expression/emotion recall
- tone/lighting/visual atmosphere recall

### Consequence

The benchmark must not be dominated by easy scene-category queries like “sunset beach” or “office meeting” alone.

## Q2 — What query classes are mandatory?

### Locked decision

P12-002 must include at minimum these benchmark query classes:

1. **Subject attribute detail**
   - examples: clothing, accessory, pose, visible object held by a subject
2. **Composition and spatial layout**
   - examples: left/right/foreground/background/near window/close-up/wide shot
3. **Subject relationships**
   - examples: person holding object, couple together, child near adult, group interaction
4. **Emotion and expression**
   - examples: smiling, serious, laughing, intimate, tense
5. **Visual tone and tonality**
   - examples: dark moody, bright warm, backlit, soft airy, high-contrast
6. **Broad semantic regression set**
   - examples: scene/category queries used to ensure later changes do not accidentally damage the broad search baseline

### Consequence

Every later workstream should report gains and regressions both overall and by query class.

## Q2A — What minimum benchmark coverage is locked?

### Locked decision

The first frozen P12-002 benchmark set must meet all of these minimum coverage rules:

- minimum total benchmark size: `30` queries
- minimum per-class coverage: `5` queries in each mandatory query class
- broad semantic regression queries must remain a minority of the benchmark and may not exceed `20%` of the total query set

### Coverage consequence

The initial benchmark cannot be satisfied by an undersized or lopsided query set that over-represents easy broad-scene retrieval.

For the first frozen benchmark release, the practical minimum shape is therefore:

- `5` subject attribute detail queries
- `5` composition/spatial layout queries
- `5` subject relationships queries
- `5` emotion/expression queries
- `5` visual tonality queries
- `5` broad semantic regression queries

Later benchmark expansions may increase coverage beyond this floor, but they must not go below it or allow the broad semantic regression bucket to dominate the set.

## Q3 — What relevance judgment model is required?

### Locked decision

P12-002 uses a three-tier human judgment model for each benchmark query against known target items:

- `primary_match`
- `acceptable_match`
- `non_match`

### Meaning of each judgment

- `primary_match`: the intended remembered photo or a clearly best equivalent target for the query
- `acceptable_match`: not the primary intended photo, but still a meaningfully acceptable retrieval for the query
- `non_match`: semantically related or unrelated but not an acceptable remembered-photo result

### Consequence

The benchmark can distinguish between:

- top-1 success on the exact intended photo
- top-5 usefulness even when the exact photo is not first
- weak semantic near-misses that should not count as success

## Q4 — What metrics are locked?

### Locked decision

P12-002 locks these minimum benchmark metrics:

- `top1_primary_hit_rate`
- `top5_primary_hit_rate`
- `top5_primary_or_acceptable_hit_rate`
- per-query-class versions of the same metrics

### Optional secondary metrics

- median rank of first `primary_match`
- median rank of first `primary_or_acceptable_match`
- regression deltas against previous benchmark run

### Consequence

Later workstreams must report these same core metrics so improvement remains comparable across phases.

## Q5 — Where is the single benchmark contract owned?

### Locked decision

The single authoritative owner document/location for the benchmark contract is:

- `docs/planning/P12-002_plan.md` under `## Benchmark Contract`

Any scripts, fixtures, or result artifacts created during implementation may support this contract, but this plan remains the single canonical owner of:

- benchmark query classes
- judgment labels
- success metrics
- required reporting format

### Consequence

The benchmark cannot quietly drift by being redefined in ad hoc result files or test-only fixtures.

3. **Evaluation harness**

4. **Baseline result capture**

## Detailed Step Plan

## Step 1: Lock the benchmark contract

### Objective

Define the stable contract for how remembered-photo retrieval quality will be judged.

### Required output

P12-002 must explicitly lock:

- the query classes
- the relevance judgment labels
- the minimum benchmark metrics
- the required report format

### Locked labels

These labels must be used consistently in benchmark data and evaluation output:

- `primary_match`
- `acceptable_match`
- `non_match`

### Locked metrics

- `top1_primary_hit_rate`
- `top5_primary_hit_rate`
- `top5_primary_or_acceptable_hit_rate`

### Constraints

- do not define a moving or heuristic-only success rule
- do not treat semantically adjacent but compositionally wrong results as automatic success

## Step 2: Build the remembered-photo query set

### Objective

Create the first curated benchmark dataset covering the required remembered-photo query classes.

### Required output

The first benchmark set must include a balanced mix of queries across:

- subject attribute detail
- composition/spatial layout
- subject relationships
- emotion/expression
- visual tone/lighting/tonality
- broad semantic regression queries

The first frozen benchmark set must contain at least `30` total queries and at least `5` queries in each mandatory query class.

### Dataset construction rules

- each query must have at least one known `primary_match`
- ambiguous queries may have multiple `acceptable_match` items if justified
- broad semantic regression queries must remain a minority of the benchmark rather than dominating it
- broad semantic regression queries may not exceed `20%` of the total benchmark set
- benchmark items should represent realistic product content, not synthetic query-only examples with no operational relevance

### Constraints

- do not overfit the query set to current known strengths only
- do not build a benchmark that requires future multimodal features to score at all

## Step 3: Create the evaluation harness

### Objective

Define and implement a repeatable offline evaluation path that runs the benchmark against the current search stack.

### Required output

The harness must:

- execute the benchmark query set against the current search surface
- record ranked results for each query
- score them using the locked labels and metrics
- emit a stable report format reusable by later workstreams

### Preferred boundary

- use a dedicated script or evaluation utility rather than burying this logic inside normal API tests
- keep the benchmark rerunnable without requiring destructive data changes

### Constraints

- do not mix benchmark evaluation with production search behavior changes
- do not redefine the benchmark contract in code comments alone; the plan remains the contract owner

## Step 4: Freeze the current baseline

### Objective

Run the benchmark on the current architecture and capture the baseline result that all later workstreams compare against.

### Required output

The frozen baseline must include:

- overall metric results
- per-query-class metric results
- notes on the major current failure patterns observed

### Constraints

- the baseline run must happen before richer metadata or ranking changes land
- later workstreams may improve the harness implementation, but not silently replace the baseline benchmark definition

## Benchmark Contract

This section is the single authoritative owner for the P12-002 evaluation contract.

### Mandatory query classes

- `subject_attribute_detail`
- `composition_spatial_layout`
- `subject_relationships`
- `emotion_expression`
- `visual_tonality`
- `broad_semantic_regression`

### Mandatory benchmark coverage floor

- minimum total benchmark size: `30` queries
- minimum per-class coverage: `5` queries in each mandatory query class
- maximum broad semantic regression share: `20%` of the total benchmark set

### Mandatory relevance labels

- `primary_match`
- `acceptable_match`
- `non_match`

### Mandatory metrics

- `top1_primary_hit_rate`
- `top5_primary_hit_rate`
- `top5_primary_or_acceptable_hit_rate`

### Required reporting shape

Every benchmark report produced by this workstream or any follow-on remembered-photo retrieval workstream must include:

1. overall values for all mandatory metrics
2. per-query-class values for all mandatory metrics
3. benchmark query count by class
4. a short failure-pattern summary describing where retrieval is still weak

## Validation

P12-002 is valid only if all of the following are true:

- a curated remembered-photo query set exists and is repeatable
- the benchmark contract is frozen in one authoritative location
- the evaluation harness can be rerun against the current system consistently
- the frozen current-state baseline has been captured using the locked metrics
- later workstreams could rerun the same benchmark without redefining it

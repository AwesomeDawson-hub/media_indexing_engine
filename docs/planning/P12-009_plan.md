## Architect Decision

`P12-009` should be implemented as a **narrow metadata-preservation hardening slice that extracts source-authored capture metadata into first-class DB fields, makes date-taken behavior depend on those DB fields, and prevents AI write-back from overwriting authoritative source capture-time and source-location metadata**.

Reasoning:

- current enrichment preserves some existing EXIF, but the app does not yet lock a complete source-truth contract for capture date/time and GPS
- reliable date-taken search cannot depend on rereading mutable enriched files
- AI `location_hint` is currently too close to authoritative source-location fields in the write-back mapping
- PNG XMP replacement is too destructive for source-authored metadata preservation

This slice is intentionally separate from `P12-002`. It hardens source-truth metadata preservation without changing the benchmark-first scope of remembered-photo evaluation.

## Objective

Define and implement the source-truth contract for capture metadata so the system can preserve original capture date/time and GPS, support correct date-taken behavior, and prevent AI inference from being written back into authoritative source-location fields.

The target outcome is:

- source-authored capture date/time and GPS are stored in first-class DB fields
- date-taken behavior depends on DB fields rather than file rereads
- AI write-back preserves authoritative source fields
- PNG XMP handling becomes merge-preserving rather than destructive

## Current Live Baseline

The current codebase shows partial preservation behavior but no fully locked contract:

- JPEG/TIFF EXIF merge preserves existing `0th` and `Exif` tags, but there is no first-class app contract for capture date/time and GPS persistence
- AI `location_hint` is currently mapped into IPTC city and XMP location fields
- PNG writer preserves text chunks but replaces the XMP packet rather than merging it
- `MediaMetadata` stores AI metadata such as `location_hint`, but no first-class capture-time or GPS DB fields are currently present
- UI copy already implies that original capture date and geo-location are preserved, but that preservation is not yet locked end-to-end in the storage/query contract

## Architect Decision Summary

## Q1 — Must original capture date/time and GPS be extracted and stored in the DB at ingest time?

### Locked decision

Yes. Source-authored capture metadata must be extracted during ingest and stored in first-class DB fields.

### Minimum required app fields

- `source_capture_datetime_utc`
- `source_capture_datetime_raw`
- `source_capture_time_offset_minutes`
- `source_gps_latitude`
- `source_gps_longitude`

### Optional additive field

- `source_gps_altitude_meters`

### Consequence

Source-truth capture metadata no longer depends on later file availability or mutable write-back state.

## Q2 — What is the search-by-date contract?

### Locked decision

Date-taken behavior must read from the first-class DB capture metadata fields, especially `source_capture_datetime_utc`.

### Locked rule

- query-time rereads of mutated or enriched files are not part of the date-taken contract
- `analyzed_at`, upload time, and write-back timestamps must not be treated as date taken
- if no trustworthy source capture datetime exists, the stored field remains null

### Consequence

Date-taken search/filtering remains stable across connector-backed reference items, preview-only items, and later enrichment changes.

## Q3 — Which metadata fields are authoritative and must never be overwritten by AI inference?

### Locked decision

AI inference must never overwrite source-authored capture-time or source-location fields.

### Locked authoritative categories

1. source-authored capture date/time fields
2. source-authored GPS coordinates
3. standard source-location descriptors such as IPTC city/sub-location/country and their XMP equivalents

### Consequence

AI metadata remains descriptive only and cannot silently corrupt source provenance.

## Q4 — Must AI `location_hint` stop writing into IPTC city or other standard source-location fields?

### Locked decision

Yes. AI `location_hint` must not be mapped into IPTC city, XMP IPTC location fields, EXIF GPS, or any other authoritative source-location field.

### Consequence

The system stops conflating inference with source-truth metadata.

## Q5 — Does PNG/XMP preservation require merge behavior instead of whole-packet replacement?

### Locked decision

Yes. Existing PNG XMP must be preserved through a merge strategy. If safe merge cannot be performed, the original XMP packet must be preserved and destructive replacement skipped.

### Consequence

The product must not destroy unrelated source-authored XMP in order to add AI-authored fields.

## Locked Implementation Shape

P12-009 should be implemented as four tightly scoped slices:

1. **First-class capture metadata fields**
   - add DB fields for normalized source capture date/time and GPS

2. **Ingest extraction and historical backfill**
   - populate source-truth fields during ingest and define a backfill path for existing rows

3. **Write-back preservation tightening**
   - preserve authoritative source fields and stop mapping AI `location_hint` into standard location fields

4. **Focused preservation tests**
   - add tests for `DateTimeOriginal`, GPS, re-analysis non-overwrite behavior, and PNG XMP merge safety

## Detailed Step Plan

## Step 1: Add first-class source capture metadata fields

### Objective

Create the app-side source-truth storage boundary for capture metadata.

### Required outcome

Add additive nullable DB fields for:

- `source_capture_datetime_utc`
- `source_capture_datetime_raw`
- `source_capture_time_offset_minutes`
- `source_gps_latitude`
- `source_gps_longitude`
- optional `source_gps_altitude_meters`

### Constraints

- keep the change additive
- keep these fields separate from AI metadata fields on `MediaMetadata`

## Step 2: Extract and normalize source capture metadata at ingest

### Objective

Populate the first-class source-truth fields from source-authored metadata during ingest.

### Required outcome

- extract `DateTimeOriginal` and related source capture metadata when available
- normalize capture datetime into UTC for query correctness
- preserve the raw source value for auditability
- extract GPS latitude/longitude when present
- define a backfill/remediation path for historical rows

### Constraints

- do not require query-time file rereads later
- do not let re-analysis overwrite source-truth fields

## Step 3: Tighten write-back preservation rules

### Objective

Prevent AI-authored metadata from overwriting authoritative source capture-time and source-location fields.

### Required outcome

- preserve existing EXIF capture-time and GPS fields across supported EXIF-preserving formats
- stop mapping AI `location_hint` into IPTC city
- stop mapping AI `location_hint` into XMP IPTC location fields
- stop deriving EXIF GPS from AI `location_hint`
- restrict AI-authored write-back to non-authoritative descriptive fields only

### Constraints

- do not broaden this into a full metadata-authoring redesign
- do not treat AI inference as source truth

## Step 4: Make PNG XMP handling non-destructive

### Objective

Preserve source-authored PNG XMP instead of replacing the whole packet.

### Required outcome

- existing XMP must be merged rather than replaced when safe merge is possible
- unrelated namespaces and properties must survive the write-back operation
- if safe merge is not possible, preserve the original packet and skip destructive rewrite

### Constraints

- do not silently drop existing XMP to make AI metadata fit

## Source-Truth Capture Metadata Contract

### Authoritative app fields

- `source_capture_datetime_utc`
- `source_capture_datetime_raw`
- `source_capture_time_offset_minutes`
- `source_gps_latitude`
- `source_gps_longitude`
- optional `source_gps_altitude_meters`

### Ownership rule

These are source-truth fields, not AI fields. They must not be overwritten by re-analysis, metadata edit flows, or AI write-back.

---

## Write-Back Preservation Rules

1. Preserve existing EXIF capture-time and GPS fields across JPEG/TIFF/WebP/AVIF write-back.
2. Preserve existing IPTC/XMP standard source-location fields.
3. Do not map AI `location_hint` into IPTC city, XMP IPTC location, or EXIF GPS.
4. Restrict AI-authored write-back to clearly descriptive, non-authoritative fields.
5. For PNG, merge existing XMP non-destructively or fail closed by preserving the original packet.

---

## Search-By-Date Contract

1. Date-taken search/filter behavior reads from `source_capture_datetime_utc`.
2. Query-time rereads of mutated files are not part of the search contract.
3. Null source capture datetime remains null unless explicit extraction/backfill populates it.
4. `analyzed_at`, upload time, and write-back timestamps must not masquerade as date taken.

---

## Validation

P12-009 is valid only if all of the following are true:

- ingest extracts and stores source capture datetime when present
- ingest extracts and stores GPS when present
- re-analysis does not overwrite stored source-truth capture fields
- JPEG/TIFF enrichment preserves pre-existing `DateTimeOriginal` and GPS EXIF data
- AI `location_hint` is no longer written into IPTC city or XMP IPTC location fields
- PNG enrichment preserves existing XMP through safe merge behavior or fail-closed preservation

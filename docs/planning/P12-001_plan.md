## Architect Decision

`P12-001` was implemented as a **targeted Google-auth readiness hardening slice that keeps the existing Google SSO and Google Drive OAuth architecture intact, makes provider-gated beta access explicit, improves recovery guidance, and produces one authoritative operator-readiness contract for hosted external beta use**.

Reasoning:

- The current Google auth surfaces already exist and are materially complete; the dominant remaining risk is deployment and beta-access ambiguity rather than missing foundational capability.
- External beta users can still encounter failures caused by Google testing, consent-screen, scope, or publishing state even when the application code is behaving correctly.
- The current system does not yet have a tight contract that distinguishes operator-owned readiness problems from user-owned consent or reconnect actions.
- The highest-value next slice is therefore not a new provider or architecture change, but explicit readiness semantics, better UX messaging, and operator-safe rollout guidance.

## Objective

Harden the Google OAuth boundary so external beta users can reliably sign in and connect Google Drive under an operator-controlled, production-ready configuration.

This workstream is intentionally about readiness, recovery clarity, and operator confidence. It does **not** expand provider scope, reopen export architecture, or revive deprecated local working-folder intake.

The implemented outcome is a product that fails clearly when Google platform configuration blocks access and guides both operators and beta users toward the correct next action.

## Architect Decision Summary

## Q1 — What exact surface is in scope?

### Locked decision

P12-001 covers the Google OAuth readiness boundary for **both**:

1. Google SSO user sign-in
2. Google Drive connector authorization, reconnect, and scope-upgrade entry points

### In scope

- readiness hardening for Google OAuth start/callback/exchange flows
- explicit handling of provider-blocked beta access states
- clearer user-facing recovery and reconnect guidance in auth and connector UX
- operator-facing readiness checklist and onboarding guidance for external beta access
- smoke-test expectations for Google sign-in and Drive connection under real deployment conditions
- targeted diagnostics or response-shape refinements needed to distinguish app issues from Google platform gating

### Explicitly out of scope

- Dropbox or any new provider
- local watched-folder or local working-folder expansion
- broad connector-health redesign beyond Google OAuth readiness
- P11-002 export architecture changes
- provider-neutral OAuth abstraction redesign

### Consequence

P12-001 is a cleanup/hardening slice around the existing Google auth surface, not a new connector initiative.

## Q2 — What user-facing failure boundary is required?

### Locked decision

Google-blocked beta access must be presented as an explicit product state, not as a vague generic login/connect failure.

### Minimum state classes

- provider app not ready for this beta audience
- provider access denied or consent rejected by the user
- connector reauthorization required
- connector scope upgrade required
- connector auth unavailable due to operator configuration or platform policy state

### Canonical locked identifiers

P12-001 locks the exact canonical identifiers below.

These names must be used consistently:

- as backend `detail.error_code` values where an API response is responsible for the failure classification
- as frontend callback/banner/recovery state identifiers where the UI is rendering the condition
- as the plan-level vocabulary for documentation, tests, and closeout review

| Condition | Locked backend/frontend identifier |
|---|---|
| provider app not ready for this beta audience | `google_oauth_app_not_ready` |
| provider access denied or consent rejected by the user | `google_oauth_access_denied` |
| connector reauthorization required | `google_drive_reconnect_required` |
| connector scope upgrade required | `google_drive_scope_upgrade_required` |
| connector auth unavailable due to operator configuration or platform policy state | `google_oauth_unavailable` |

### Locked naming rule

- Do not introduce alternate synonyms for these states in backend or frontend code.
- Do not split these into different auth-vs-connector labels unless a later dedicated workstream intentionally revises the contract.
- Human-readable copy may vary by screen, but the machine-readable identifier must remain one of the locked values above.

### Required UX rule

When Google platform state is the blocker, the product must prefer actionable explanation over opaque failure wording.

### Consequence

P12-001 should make it obvious whether the next action belongs to the beta user or to the operator.

## Q3 — What operator-facing readiness contract is required?

### Locked decision

P12-001 must produce a single current readiness contract for external beta access across Google SSO and Google Drive.

### Minimum operator checklist topics

- required callback and redirect URI alignment
- required authorized domain / origin expectations
- testing-mode versus published-mode implications
- test-user allowlist expectations when Google still gates access
- scope and consent-screen requirements for Drive connection and scope upgrade
- environment-variable and feature-flag prerequisites
- minimal smoke-test flow before inviting new beta users

### Single authoritative owner document

The single authoritative owner document/location for the operator-readiness and beta-onboarding contract is:

No second doc becomes an equal owner for this checklist during P12-001. Other live docs may reference it, but they must not become competing sources of truth.

### Consequence

Operator setup stops being tribal knowledge spread across historical docs and becomes a current deployable checklist.

## Q4 — What product boundary must remain unchanged?

### Locked decision

### Deprioritized for now

- async export polish beyond current ADR-036 closeout baseline

### Consequence

## Locked Implementation Shape

P12-001 was implemented as four tightly scoped slices:

1. **Readiness diagnostics and response contract**
   - make Google-platform blocking states explicit
   - distinguish operator-side configuration problems from user-side consent or reconnect actions

2. **User-facing recovery UX**
   - improve auth/connect banners, error text, and reconnect/scope-upgrade guidance
   - keep the product clear about what is blocked and why

3. **Operator readiness checklist**
   - document the exact Google setup and beta-onboarding prerequisites for the hosted deployment
   - define a current smoke-test checklist for sign-in and Drive connection

4. **Validation hardening**
   - add or refine focused tests around Google OAuth readiness and blocked-state handling where the current contract is ambiguous
   - do not treat unrelated `tests/test_google_drive_connector.py` drift as automatically in scope unless P12-001 directly touches that path

- provider policy / publishing / verification gating

- user-denied consent
- reconnect-required connector state
- scope-upgrade-required connector state

### Required outcome

The workstream does not leave Google failures as an undifferentiated generic auth/connect bucket.

### Implementation expectations

- review the current Google SSO and Drive connector start/callback/exchange flows
- identify where Google-provider gating, operator misconfiguration, and user-decision failures are currently collapsed together
- lock a documented error/state vocabulary that can be consumed consistently by backend responses and frontend banners
- preserve existing project-standard `detail` + `error_code` behavior where API changes are needed

### Locked Step 1 output

The implementation must use these exact identifiers for the minimum readiness/recovery cases:

- `google_oauth_app_not_ready`
- `google_oauth_access_denied`

- `google_drive_scope_upgrade_required`

- contact the operator because the beta app is not yet permitted for them

### Implementation expectations

- audit the current banners, callback-result handling, and auth/connect error presentation
- improve messaging around Google SSO callback failures and Drive connector callback failures
- improve reconnect/scope-upgrade language on connector pages where current state is too technical or too vague

## Step 3: Produce an operator-readiness checklist

### Objective

Create one current deployable contract for Google auth readiness in the hosted beta environment.

### Required outcome

An operator can now answer, from one current source of truth:

- whether Google SSO is expected to work for external testers
- whether Google Drive connection is expected to work for external testers
- what exact Google-console, consent-screen, and redirect configuration must be present
- what to verify before inviting a new tester cohort

### Implementation expectations

- document the current Google setup prerequisites without reopening the original P6-001 or P7-002 architecture decisions
- include callback URI, authorized domain/origin, consent-screen, test-user, publishing-status, and scope-readiness expectations
- define a minimal hosted-beta smoke checklist for sign-in and Drive connection
- place the operator-facing checklist in a current doc location that fits the existing governance/doc hierarchy

### Preferred documentation outcome

- keep the authoritative contract referenced from the P12-001 plan
- update top-level or live-governance docs only where current-state visibility is useful
- avoid scattering the readiness checklist across multiple historical workstream records

### Locked checklist owner

P12-001 names this single authoritative checklist destination:

- `docs/planning/P12-001_plan.md` -> `## Hosted Beta Operator Readiness Checklist`

All operator-readiness and beta-onboarding checklist content required by this workstream must live there.

### Required checklist topics

The checklist section must cover at minimum:

- Google SSO callback URI and frontend completion URI alignment
- Google Drive connector callback URI and scope-upgrade callback alignment
- authorized domain and authorized origin expectations
- consent-screen publishing/testing state and external beta implications
- test-user allowlist expectations when Google still restricts the app audience
- required env vars and feature flags for hosted beta readiness
- minimum smoke-test sequence before inviting additional testers

## Hosted Beta Operator Readiness Checklist

This section is the single authoritative owner for the P12-001 operator-readiness and beta-onboarding contract.

### Google platform readiness

- Verify the Google app configuration used for beta matches the actual deployed frontend and backend callback URIs.
- Verify the app is in the intended Google testing/publishing state for the target beta audience.
- If Google still restricts usage to test users, verify the intended testers are on the allowlist before invitation.

### Redirect and origin alignment

- Verify Google SSO start/callback/exchange flow uses the correct backend callback and frontend completion route for the deployed environment.
- Verify Google Drive connector OAuth and scope-upgrade flows use the correct backend callback targets for the deployed environment.
- Verify authorized origins/domains configured in Google match the externally reachable beta hostname.

### App configuration readiness

- Verify the required Google auth environment variables are populated for the deployed environment.
- Verify Google SSO and Google Drive connector feature gates are enabled only when the environment is actually ready.
- Verify no stale local/dev callback URL configuration remains in the active deployment.

### Beta smoke test before inviting users

- Confirm a beta user can complete Google SSO start -> callback -> exchange successfully.
- Confirm a beta user can start Google Drive connection, complete callback, and reach configured connected state successfully.
- Confirm a blocked tester receives the correct explicit readiness-state messaging rather than a generic auth failure.
- Confirm reconnect-required and scope-upgrade-required flows show the correct guided next action.

## Step 4: Add focused validation and lock rollout expectations

### Objective

Make P12-001 reviewable and deployable through focused test and smoke evidence rather than broad subjective confidence.

### Required outcome

P12-001 defined exactly what validation was required before the slice was considered ready for closeout.

### Minimum validation categories

- focused backend tests for any newly differentiated Google-auth outcomes
- focused frontend behavior checks for new banners or recovery messaging
- hosted-beta smoke checks for:
   - Google SSO start -> callback -> exchange
   - Drive quick-connect or connector start -> callback -> configured state
   - blocked-state behavior when the app is not ready for the tester audience
   - scope-upgrade and reconnect guidance where applicable

### Constraints

- do not expand validation into a full unrelated connector-suite cleanup initiative
- if unrelated failures remain, document them clearly as out of scope unless P12-001 directly caused them

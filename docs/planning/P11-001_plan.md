## Objective

This document now records the locked contract that shipped in P11-001 and governs post-implementation closeout.

P11-001 is intentionally limited to `POST /api/v1/media/reanalyze-batch`.

It does **not** include bulk export. Bulk export is explicitly deferred into the separate follow-on workstream `P11-002 — Async Connector-Aware Bulk Export`.

The plan preserves the existing ARCH-002 boundary:

- originals for reference-mode items remain source-owned
- no hidden fallback to app-retained originals is allowed
- local-folder reference items do not gain fake hosted-original behavior
- Drive-backed reference refetch remains explicit and connector-specific, not provider-neutral by default

Implementation completed on 2026-04-12. P11-001 is no longer an approval gate. The authoritative live outcome is:

- explicit per-item `accepted`/`blocked`/`rejected` reporting replaced silent skips
- Drive-backed reference items are admitted only through async queueing
- local-folder and other non-Drive reference providers remain blocked
- quota remains all-or-nothing with explicit HTTP 429 reclassification behavior
- missing and unauthorized IDs intentionally collapse to rejected `media_item_not_found`

---

## Pre-Implementation Legacy Baseline

Before P11-001 was implemented, `src/api/routes/analysis.py` behaved as a legacy full-storage batch endpoint:

- it only queues items whose original is already in app storage
- it silently skips reference or preview-only items
- it silently skips items with an in-progress analysis job
- it returns only `{queued, message}` and does not explain which items were skipped or why

That behavior is a historical baseline only. It is **not** the shipped P11-001 contract.

### Locked product conclusion

Silent skip behavior is not an acceptable final contract.

## Delivered Implementation Summary

The implemented route now:

- returns `BatchReanalyzeResponseV2` on success with `request_count`, `accepted_count`, `blocked_count`, `rejected_count`, `queued_count`, and ordered per-item outcomes
- keeps full/app-retained items eligible
- admits Drive-backed `storage_mode='reference'` items through async background execution only
- blocks local-folder and unsupported non-Drive providers explicitly
- blocks in-progress items explicitly
- returns HTTP 429 `quota_exceeded` with no partial queueing when accepted candidates exceed remaining quota

## Architect Decision Summary

## Q1 — What surface is in scope?

### Locked decision

P11-001 covers exactly one API surface:

1. `POST /api/v1/media/reanalyze-batch`

### Explicitly out of scope

- `POST /api/v1/media/download-batch`
- all bulk export and ZIP packaging behavior
- `GET /api/v1/media/{id}/download`
- `POST /api/v1/media/{id}/reanalyze`
- `POST /api/v1/media/{id}/convert-png`
- provider-neutral bulk refetch for every reference provider

### Consequence

P11-001 must not smuggle in bulk export design decisions. Those belong to P11-002.

## Q2 — Which item classes are eligible?

### Locked decision

P11-001 defines four item classes:

1. **Full/app-retained items**
   - eligible
2. **Drive-backed `storage_mode='reference'` items**
   - eligible only through a capability-aware queueing path that fetches transient bytes during job execution, not during request validation
3. **Local-folder reference items**
   - blocked
4. **Future non-Drive reference providers**
   - blocked unless a later dedicated workstream explicitly expands them

### Why this is the correct boundary

- full items already have a valid local-storage reanalysis path
- Drive-backed reference items are the only connector-backed reference class with an established transient fetch contract after P10-001
- local-folder items still depend on user-mediated source access and must not be treated as if the server owns a bulk-readable original
- other providers must not inherit provider-neutral batch refetch behavior without explicit product and ops review

## Q3 — Are mixed selections allowed?

### Locked decision

Yes, mixed selections are allowed, but only with explicit per-item outcome reporting.

The route must not fail simply because the user selected a mix of eligible and ineligible items.

Instead, the request classifies every requested item into one of these outcomes:

- `accepted` — eligible and queued
- `blocked` — owned item, but not eligible for batch reanalysis under the locked contract
- `rejected` — invalid for the request or not accessible to the caller

### Examples

- full item + Drive-backed reference item: allowed
- full item + local-folder reference item: allowed, but local-folder item is explicitly blocked
- Drive-backed reference item + unsupported future provider item: allowed, but unsupported provider item is explicitly blocked

### Consequence

Mixed selections are a reporting problem, not a silent-skip problem.

## Q4 — What is the API response contract?

### Locked decision

`POST /api/v1/media/reanalyze-batch` remains a synchronous queueing request only. It does **not** perform analysis inline.

On success it returns a structured response that includes, at minimum:

- `request_count`
- `accepted_count`
- `blocked_count`
- `rejected_count`
- per-item outcome entries for every requested item

### Required per-item outcome shape

Each item outcome must include:

- `media_id`
- `outcome` (`accepted`, `blocked`, `rejected`)
- `reason_code`
- operator-safe `message`
- `job_id` when queued successfully

### Minimum blocked reason classes

- `analysis_in_progress`
- `local_reference_not_supported`
- `provider_batch_reanalysis_not_supported`
- `connector_refetch_not_available`

### Minimum rejected reason classes

- `media_item_not_found`

### Locked closeout clarification

The implementation and tests intentionally use one privacy-preserving rejection code for both missing IDs and unauthorized IDs:

- `media_item_not_found`

`not_owned` does **not** remain part of the authoritative shipped contract.

### Consequence

The endpoint becomes explicit and debuggable. Users no longer have to infer why part of a batch was ignored.

## Q5 — What is the quota contract?

### Locked decision

Blocked and rejected items do not consume quota.

For accepted candidates, quota must be reserved before any jobs are committed.

### Locked batch rule

Quota for accepted candidates is **all-or-nothing** at the request level.

If quota cannot cover every accepted candidate, the route must queue none of them and must return a quota failure rather than partially queueing the first subset that happened to be iterated first.

### Exact API contract for quota exhaustion

If at least one item would otherwise be `accepted` but the user lacks enough quota to reserve all accepted candidates, the route must return **HTTP 429**.

The failure payload must use the standardized `detail` dict contract and include:

```json
{
   "error_code": "quota_exceeded",
   "message": "Not enough quota to queue all eligible items in this batch.",
   "request_count": 0,
   "accepted_candidate_count": 0,
   "blocked_count": 0,
   "rejected_count": 0,
   "queued_count": 0,
   "outcomes": []
}
```

### Required field semantics

- `request_count`: total requested item count
- `accepted_candidate_count`: count of items that were otherwise eligible before quota enforcement
- `blocked_count`: total blocked item count after quota handling
- `rejected_count`: total rejected item count
- `queued_count`: must be `0` on quota exhaustion
- `outcomes`: required per-item reporting array for every requested item

### Quota interaction with per-item reporting

- previously blocked items remain `blocked` with their original reason codes
- previously rejected items remain `rejected`
- every would-be accepted item must be returned as `blocked` with reason code `quota_exhausted_batch`
- no `job_id` may be present for any item in a quota-exhausted response

### Implementation-ready response example

```json
{
   "detail": {
      "error_code": "quota_exceeded",
      "message": "Not enough quota to queue all eligible items in this batch.",
      "request_count": 5,
      "accepted_candidate_count": 3,
      "blocked_count": 4,
      "rejected_count": 1,
      "queued_count": 0,
      "outcomes": [
         {
            "media_id": "full-1",
            "outcome": "blocked",
            "reason_code": "quota_exhausted_batch",
            "message": "This item was eligible but the batch was not queued because the full set of eligible items exceeded remaining quota."
         },
         {
            "media_id": "drive-1",
            "outcome": "blocked",
            "reason_code": "quota_exhausted_batch",
            "message": "This item was eligible but the batch was not queued because the full set of eligible items exceeded remaining quota."
         },
         {
            "media_id": "local-1",
            "outcome": "blocked",
            "reason_code": "local_reference_not_supported",
            "message": "Local-folder reference items are not eligible for server-side batch reanalysis in P11-001."
         },
         {
            "media_id": "running-1",
            "outcome": "blocked",
            "reason_code": "analysis_in_progress",
            "message": "Analysis is already in progress for this item."
         },
         {
            "media_id": "missing-1",
            "outcome": "rejected",
            "reason_code": "media_item_not_found",
            "message": "Media item not found or not accessible to the caller."
         }
      ]
   }
}
```

### Why this is the correct boundary

- partial queueing based on iteration order is operationally unpredictable and poor UX
- users need a stable answer about whether the eligible portion of their request was queued

## Q6 — What is the execution model?

### Locked decision

The request remains synchronous only as a queueing action. Analysis work executes asynchronously.

### Required execution paths

- full items continue using the existing local-storage-backed analysis path
- Drive-backed reference items must fetch transient bytes during background execution, not during the request thread

### Locked request/thread rule

The batch route must not download Drive originals inline while handling the HTTP request.

### Consequence

P11-001 extends queueing and job orchestration, not request-duration network fan-out.

## Q7 — What are the concurrency and upstream-rate-limit rules?

### Locked decision

P11-001 must enforce bounded execution for Drive-backed reference items.

### Required safeguards

- keep the current maximum request size bounded
- Drive-backed batch-created reanalysis jobs must run under explicit bounded concurrency rather than unbounded parallel fetch fan-out
- per-connector or per-source throttling must be considered part of the workstream contract, not an optional implementation detail

### Initial architectural expectation

The implementation should use a conservative bounded Drive-fetch concurrency policy, with no unbounded same-connector burst execution.

### Why this is the correct boundary

- Drive-backed batch reanalysis multiplies upstream 429 and timeout risk quickly
- bounded execution is required to preserve reliability and predictable failure handling

## Q8 — What are the timeout and retry expectations?

### Locked decision

Timeouts and transient connector failures remain item-scoped failures.

### Required contract

- the batch request itself does not retry failed items automatically
- a failed Drive-backed item becomes a normal failed job with explicit per-item status
- future retry UX can be added later, but P11-001 must not create a hidden batch retry storm

### Consequence

P11-001 adds capability-aware admission and execution, not a new durable batch retry subsystem.

## Delivered Service and API Changes

## 1. Replace silent skip with explicit outcome classification

The existing batch route stopped silently skipping ineligible items.

It now performs a preflight classification pass and returns per-item outcomes.

## 2. Add Drive-backed eligibility without request-time fetch

Drive-backed reference items became eligible only through a queueing model that creates jobs first and fetches bytes later during job execution.

## 3. Preserve local-folder and non-Drive blocks

`local_folder` reference items and other non-Drive reference providers remain explicitly blocked in P11-001.

## 4. Do not change batch export here

`POST /api/v1/media/download-batch` is not part of this plan.

P11-001 did not widen or redefine export behavior.

## Compatibility Rules

## Legacy route behavior

The pre-P11 route remains the historical implementation baseline, but not the shipped contract.

The implemented route preserves user ownership scoping, batch-size limits, and asynchronous analysis execution.

## Local-folder behavior

Local-folder reference items remain user-mediated source items.

P11-001 must not imply that the backend can bulk-read those originals from hosted storage.

## Future providers

Non-Drive providers remain blocked by default.

Any future provider expansion must be explicit and connector-specific.

- mixed selection response with accepted + blocked items

Closeout validation re-ran:

## 3. Manual operator validation

Closeout verification should confirm:

1. a mixed batch request returns explicit accepted/blocked/rejected results
2. full items queue normally
3. Drive-backed reference items queue without request-time download work
4. local-folder reference items are blocked explicitly, not silently skipped
5. quota exhaustion does not produce partial first-N queueing

## Architect Verdict

P11-001 was the correct post-P10 workstream and is now implemented.

Batch reanalysis was expanded safely before bulk export because it could build on the existing asynchronous analysis-job model while preserving ARCH-002's source-owned-original boundary. Bulk export remains a different operational problem and therefore remains a separate later workstream.

The critical discipline is unchanged: explicit capability boundaries, explicit per-item outcomes, no silent skips, no provider-neutral assumptions, and no hidden reintroduction of app-retained originals.

## Objective

Reconcile the now-implemented P10-001 Drive refetch slice to one authoritative architecture and API contract.

P10-001 remains intentionally narrow. It does **not** reopen ARCH-002 or reintroduce app-retained originals. Instead, it locks the authoritative contract for the already-landed Drive-only refetch path that:

- keeps full-size originals source-owned and transient only
- reuses the existing `analyze_connector_item()` pipeline for re-analysis
- enables a server-generated enriched download/export for Drive-backed reference items
- leaves non-Drive reference items behind the existing controlled 409 `original_at_source` guard

The live codebase no longer needs a pre-implementation design pass. The shared refetch service and both route integrations already exist:

- [Projects/media_indexing_engine/src/connectors/drive_reference_fetch.py](Projects/media_indexing_engine/src/connectors/drive_reference_fetch.py#L1) provides the shared transient Drive fetch service
- [Projects/media_indexing_engine/src/api/routes/analysis.py](Projects/media_indexing_engine/src/api/routes/analysis.py#L116) already routes Drive-backed reference re-analysis through that shared service
- [Projects/media_indexing_engine/src/api/routes/download.py](Projects/media_indexing_engine/src/api/routes/download.py#L75) already routes Drive-backed reference download/export through that shared service
- [Projects/media_indexing_engine/src/api/storage_guards.py](Projects/media_indexing_engine/src/api/storage_guards.py#L1) still provides the default 409 guard for non-fetchable original-dependent paths

This document now serves as the historical authoritative contract that governed reconciliation and closeout. Implementation and governance alignment are complete; the locked API standard below remains the baseline for any future related work.

## Architect Decision Summary

## Q1 — Which user-facing surfaces are in scope?

### Locked decision

P10-001 includes exactly these two surfaces for `provider_type='google_drive'` reference items:

1. `POST /api/v1/media/{id}/reanalyze`
2. `GET /api/v1/media/{id}/download`

### Explicitly out of scope in this slice

- `POST /api/v1/media/reanalyze-batch`
- `POST /api/v1/media/download-batch`
- `POST /api/v1/media/{id}/convert-png`
- any local-folder refetch flow
- any S3-compatible or other non-Drive connector refetch flow
- any background prefetch, cache warming, or retained-original shadow copy

### Why this is the correct boundary

- single-item re-analysis already has a narrow, ad hoc Drive implementation, so formalizing that path is low-risk and high-value
- single-item download/export is the next most natural user operation that genuinely needs original bytes
- batch download and batch re-analysis multiply quota, timeout, and partial-failure complexity without being necessary to prove the architecture
- `convert-png` creates a new derivative artifact and should not silently inherit remote-fetch behavior without a separate product decision

### Consequence

- single-item re-analysis and single-item download are already implemented for Drive-backed reference items and remain the locked scope
- batch and conversion surfaces remain unchanged and continue using the existing guard behavior

## Q2 — What is the fetch pattern?

### Locked decision

Drive refetch in P10-001 uses **in-memory transient bytes only**.

No temporary original file is written to app storage, no `file_store.save()` call is allowed, and no persistent server-side cache of full-size originals is introduced.

### Why this is the correct boundary

- it preserves the ARCH-002 invariant that the server does not retain the original for reference-mode items
- it matches the existing contracts of [Projects/media_indexing_engine/src/analysis/processor.py](Projects/media_indexing_engine/src/analysis/processor.py#L372) and the metadata embedder, both of which already operate on bytes in memory
- it avoids cleanup risk and filesystem edge cases that come with temp-file orchestration

### Consequence

- the fetch helper returns bytes and metadata only for the lifetime of the request/background task
- memory use is bounded to the same class of workload already accepted during connector sync and current ad hoc Drive re-analysis

## Q3 — How should the storage guard be refactored?

### Locked decision

`original_is_accessible()` and `assert_original_accessible()` remain semantically unchanged: they continue to mean "the original is already in app storage and can be read locally."

P10-001 adds a **separate, narrow reference-fetch service** for the Drive exception rather than weakening the meaning of the existing guard helpers.

### Required route decision flow

For any original-requiring surface touched in this slice:

1. if the item is app-retained (`storage_mode='full'` with `storage_path`), use the existing local-storage path
2. else if the item is `storage_mode='reference'` and `OriginAssetRef.provider_type='google_drive'`, call the new Drive reference fetch service
3. else preserve the existing 409 `original_at_source` outcome

### Why this is the correct boundary

- the current helpers in [Projects/media_indexing_engine/src/api/storage_guards.py](Projects/media_indexing_engine/src/api/storage_guards.py#L29) are still the correct default for all non-fetchable cases
- mixing DB lookups, connector resolution, token refresh, and remote I/O into `storage_guards.py` would blur a simple local-storage predicate into a network orchestration layer
- keeping the exception path separate ensures `local_folder` and future reference providers do not accidentally inherit Drive-only behavior

### Consequence

- non-Drive reference items such as `provider_type='local_folder'` continue returning 409 `original_at_source`
- the shared service boundary already exists in [Projects/media_indexing_engine/src/connectors/drive_reference_fetch.py](Projects/media_indexing_engine/src/connectors/drive_reference_fetch.py#L1); the remaining task is to align its error payload and misuse classification to this locked contract

## Q4 — What are the exact error contracts for Drive refetch?

### Locked decision

P10-001 standardizes Drive refetch failures into explicit HTTP/error-code pairs.

### Contract table

| Condition | HTTP | `error_code` | Operator-safe message intent |
|---|---:|---|---|
| Drive file deleted, missing, or trashed | `404` | `drive_file_not_found` | Original no longer exists at the Drive source |
| Token refresh failure, missing refresh token, decrypt failure, or Drive auth rejection | `409` | `drive_auth_expired` | Connector authorization is no longer valid; reconnect required |
| Drive API rate limit or quota throttling | `429` | `drive_rate_limited` | Drive is rate-limiting this fetch; retry later |
| Drive fetch timeout | `504` | `drive_fetch_timeout` | Timed out while fetching the original from Drive |
| Other upstream Drive/API failures | `502` | `drive_fetch_failed` | Source fetch failed unexpectedly |

### Additional classification rules

- a trashed file is treated the same as a missing file for product purposes: `404 drive_file_not_found`
- non-Drive reference items do **not** use this table; they continue to receive `409 original_at_source`
- route-level Drive eligibility remains separate from service-level Drive fetch: non-Drive reference items should be rejected before the shared Drive service is called
- the shared Drive fetch service must raise detail payloads using `error_code` and `message`, not `error` and `message`
- service-level safety-check failures such as missing `OriginAssetRef`, non-Drive `OriginAssetRef`, missing `provider_object_id`, missing `source_id`, or missing `SourceConnector` are **implementation inconsistencies**, not request-validation errors; they must raise `502 drive_fetch_failed` and be logged for remediation rather than returning `422`
- `409 drive_auth_expired` is reserved for actual connector auth failure states such as token refresh failure, decrypt failure, missing refresh token, or explicit provider auth rejection

### Why this is the correct boundary

- the codebase standard is explicit `detail` plus `error_code`; using `detail.error` in the shared Drive service is inconsistent with the global error handler and frontend API client expectations
- `422` is appropriate for malformed client input, not for an internal mismatch between route gating and the supposedly Drive-backed item state

## Q5 — Should successful re-analysis trigger `download_and_embed_drive_metadata()`?

### Locked decision

No additional post-success call to `download_and_embed_drive_metadata()` is allowed for the P10-001 re-analysis path.

### Why this is the correct boundary

- [Projects/media_indexing_engine/src/analysis/processor.py](Projects/media_indexing_engine/src/analysis/processor.py#L435) already makes `analyze_connector_item()` the canonical reference-item pipeline
- that pipeline already invokes Drive rename and metadata embed using the same transient bytes that were fetched for analysis
- scheduling `download_and_embed_drive_metadata()` afterward would create a second redundant Drive download for the same action and would widen failure surface unnecessarily

### Consequence

- the re-analysis route only fetches once
- `analyze_connector_item()` remains the single source of truth for post-analysis rename/embed behavior
- `download_and_embed_drive_metadata()` remains reserved for flows that changed metadata without already holding the original bytes in memory, such as manual metadata edits

## Q6 — Is batch re-analysis in scope?

### Locked decision

No. `POST /api/v1/media/reanalyze-batch` remains out of scope and unchanged in P10-001.

### Why this is the correct boundary

- batch Drive refetch would need explicit concurrency, quota, and per-item failure aggregation policy that does not exist yet
- the current batch route intentionally skips non-full items; changing that behavior would enlarge the slice beyond the minimum necessary architecture proof

### Consequence

- the batch route stays stable for this workstream
- if operators want Drive-backed batch re-analysis later, that should be a dedicated follow-on slice with separate throughput and UX decisions

## Locked Scope

## 1. Shared Drive reference fetch service is already present

The shared backend service is already implemented and remains the canonical fetch boundary. Its locked responsibilities are:

- verifying the item is a Drive-backed reference item
- loading `OriginAssetRef` and connector context
- obtaining a valid access token through `DriveTokenManager`
- classifying Drive fetch failures into the locked HTTP/error-code contract
- returning transient original bytes to the caller without persisting them

### Locked service boundary

The service is a fetch/orchestration layer, not a persistence layer. It may log, classify, and raise controlled errors, but it must not write the original into app storage.

## 2. Re-analysis route integration is already present

[Projects/media_indexing_engine/src/api/routes/analysis.py](Projects/media_indexing_engine/src/api/routes/analysis.py#L116) already integrates the shared service. The remaining locked requirements are:

- the existing full-mode local-storage path stays intact
- the route must continue delegating Drive-backed reference fetch to the shared service rather than reintroducing route-local connector logic
- Drive-backed reference items obtain bytes via the shared service
- the route continues to queue `analyze_connector_item()` with those bytes

## 3. Single-item download/export integration is already present

[Projects/media_indexing_engine/src/api/routes/download.py](Projects/media_indexing_engine/src/api/routes/download.py#L75) already integrates the shared service. The remaining locked requirements are:

- full-mode items continue reading from app storage exactly as they do today
- Drive-backed reference items fetch original bytes transiently from Drive, embed metadata server-side, and return the enriched file response
- local-folder reference items continue using the existing client-supplied `/embed` flow rather than server-side refetch

## 4. Preserve current guard behavior for every other original-dependent surface

P10-001 must not broaden remote fetch behavior beyond the two locked surfaces.

The following must remain unchanged:

- `POST /api/v1/media/reanalyze-batch`
- `POST /api/v1/media/download-batch`
- `POST /api/v1/media/{id}/convert-png`
- any non-Drive reference item path

## 5. Add focused test coverage for success and failure classification

The dedicated P10-001 test module already exists. Closeout validation reconciled and re-ran route and service tests proving that:

- Drive-backed re-analysis succeeds without `storage_path`
- Drive-backed single download succeeds without `storage_path`
- no full-size original is persisted during either path
- non-Drive reference items still get 409 `original_at_source`
- each locked Drive failure class maps to the correct status/error_code pair

## Service and API Changes

## 1. New shared fetch module

The dedicated shared module already exists:

- current location: `src/connectors/drive_reference_fetch.py`
- public responsibility: resolve one Drive-backed `MediaItem` into transient bytes or a controlled fetch failure

### Required responsibilities

- load `OriginAssetRef` for the media item
- confirm `provider_type='google_drive'`
- load the active `SourceConnector`
- decrypt connector credentials
- obtain an access token using `DriveTokenManager.get_access_token(db)` so refresh-token rotation remains persistable
- perform a lightweight Drive metadata probe when needed to distinguish missing/trashed from other failures
- download media bytes with an explicit timeout
- raise a controlled `HTTPException` detail dict using `error_code` and `message` keys so the global error handler preserves the intended API contract

### Explicit non-responsibilities

- no `MediaItem` mutation
- no caching of original bytes
- no `file_store.save()`
- no write-back execution

## 2. Re-analysis route contract

`POST /api/v1/media/{id}/reanalyze` must follow this contract:

- if item is `full`, keep existing behavior
- if item is `reference` and Drive-backed, fetch bytes via the shared service, reserve quota, create job, queue `analyze_connector_item()`
- if item is any other reference item, keep 409 `original_at_source`
- preserve the existing "analysis already in progress" and quota semantics

### Locked implementation note

The route must continue using the shared service and must not hand-roll connector download logic again.

## 3. Download route contract

`GET /api/v1/media/{id}/download` must follow this contract:

- if item is `full`, keep existing behavior
- if item is Drive-backed `reference`, fetch bytes transiently, load metadata, embed metadata, and return the enriched file
- if item is `reference` but not Drive-backed, keep current controlled failure behavior

### Locked product meaning

For Drive-backed reference items, `/download` becomes a true on-demand export operation rather than a local-storage read.

## 4. No schema work in P10-001

This slice should not add tables, columns, or migrations.

The required information already exists in:

- `MediaItem.storage_mode`
- `OriginAssetRef.provider_type`
- `OriginAssetRef.provider_object_id`
- `SourceConnector` credentials and connector type

## Compatibility Rules

## Non-Drive reference items

`local_folder` and every non-Drive reference provider remain blocked behind the existing source-aware guard.

### Locked rule

P10-001 must not introduce a generic "reference items are fetchable" assumption. The exception is explicitly Drive-only.

## Existing local-folder flow

The client-mediated local-folder export path stays intact:

- [Projects/media_indexing_engine/src/api/routes/download.py](Projects/media_indexing_engine/src/api/routes/download.py#L117) remains the correct path for user-supplied local bytes
- P10-001 does not replace local-folder user re-supply with server-side filesystem reach-through

## Existing mutation flow

Manual metadata edits for Drive-backed items may continue using `download_and_embed_drive_metadata()` as their best-effort background follow-up.

P10-001 changes only the paths that already need original bytes for re-analysis or download/export.

## ADRs to Add to `DECISION_LOG.md`

## ADR-034 — Selective On-Demand Drive Refetch for Reference Items

Record these locked decisions:

- Drive-backed reference items may be refetched transiently for specific original-dependent operations
- P10-001 scope is limited to single-item re-analysis and single-item download/export
- `analyze_connector_item()` remains the canonical re-analysis pipeline for reference items
- the existing app-storage guard semantics remain unchanged for non-Drive reference items
- no persistent original cache or temp-file retention is introduced
- shared Drive fetch failures must surface through the standardized `detail` plus `error_code` contract
- shared-service misuse or inconsistent supposedly-Drive item state is a `502 drive_fetch_failed` implementation inconsistency, not a `422` client validation error

## Architect Verdict

Keep P10-001 as the first post-Phase-9 source-refetch slice, but move it out of pre-implementation approval-gate governance.

The live repo already contains the shared fetch service, route integrations, dedicated tests, and the intended narrow scope. The implemented error contract was reconciled, governance was aligned, and the workstream was closed properly on 2026-04-12.

The critical discipline remains unchanged: Drive-only, single-item only, transient-bytes only, with standardized `error_code` payloads and no `422` leakage for internal Drive-state inconsistencies.
